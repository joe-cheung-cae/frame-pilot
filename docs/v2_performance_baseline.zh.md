# FramePilot v2 性能基线

> 语言：[English](v2_performance_baseline.md) | **中文**

本文档记录 v2.5 可靠性验证的本地合成 smoke 结果。这些数字不是正式基准测试；它们提供可复现的基线，用于检查大批量本地工作流能否在无崩溃、无失败项、无明显内存增长的情况下完成。

## 发布就绪结论

- 100、500 和 1,000 张生成图的真实浏览器-后端验证通过。
- 重复的 500 张大图真实浏览器-后端验证稳定。
- 2,000 张预置元数据筛选验证通过。
- 2,000 张真实浏览器-后端导入/处理/审阅仍推迟到显式手动运行，不是默认的 v2.0 发布门槛。
- 大批量导入仍然计算密集，但上传/登记现在会快速返回，衍生件工作会带着可见的本地进度继续进行。

## 桌面 sidecar / API 性能（multipart 导入）

桌面交付的 FastAPI sidecar 由 `perf:api` 驱动。下方冒烟使用 multipart `POST /api/projects/{id}/import`（上传路径），**不是**桌面文件系统 `POST .../imports/from-paths`。耗时与 RSS 仅作 **API/sidecar** 证据。真正的路径导入 RSS 仍为 **pending**（[#97](https://github.com/joe-cheung-cae/frame-pilot/issues/97)）。

在无 WebView 的主机上（常见无 rustc ≥1.88 的 WSL agent），只记录 **sidecar / API 进程 RSS**，并将 UI 标为 pending（锁定 GUI 决策 13）。

下方行所用命令（API 进程内的合成 multipart 导入 + 处理 + 导出）：

```bash
npm run perf:api -- --output /tmp/framepilot-desktop-perf-100 --count 100
```

npm run test:e2e -- tests/e2e/local-workflow.spec.ts -g "validates the culling workspace with 2,000 seeded photos" --project=chromium

该 smoke 通过 Playwright 路由 mock 使用预置的非私人项目、照片和分组记录。生成的资源路由返回现有的微小合成图像响应，因此这里验证的是筛选工作区的浏览器行为，而不是导入吞吐、真实照片解码，或大型预览图像的传输成本。

已验证的浏览器操作：

- 筛选工作区以 2,000 张照片的项目打开。
- 第一张预览图像已渲染。
- 将一张照片标记后，Picks 筛选器完成切换。
- 状态更新通过 mock 的 API 路由持久化。
- 键盘分组导航从分组 1 移动到分组 2。
- 加载全部 2,000 张照片和全部 1,000 个分组时未崩溃。

浏览器内存说明：本次本地 Playwright 运行中 Chromium 暴露了 `performance.memory`，但这只是 JS 堆估计值，不是完整浏览器进程 RSS、图像解码内存、GPU 内存，也不是跨浏览器指标。请把报告的堆值仅视为 smoke 信号。真实照片尺寸和浏览器进程内存仍未测量。

当前浏览器规模结论：在本机上，对预置元数据记录和微小生成资源而言，2,000 张照片筛选可接受。剩余风险是真实照片的浏览器成本，来自更大预览、解码内存，以及更接近真实的网络/文件服务行为。

该 smoke 在测试时生成合成 JPEG 源照片，用临时项目数据文件夹创建项目，通过前端和真实后端导入生成文件，运行真实处理，打开真实筛选工作区，等待由 `/api/assets` 提供的预览，将一张照片标记为 Pick，切换到 Picks 筛选器，导航到另一个分组，并创建 CSV 导出。

默认范围：`npm run test:e2e:real-browser` 将真实浏览器-后端 smoke 保持在 100 张生成照片，以便本地 E2E 仍然足够快。500 张照片工作流是通过 `FRAMEPILOT_BROWSER_PERF_COUNT=500 npm run test:e2e:real-browser` 可选启用的本地验证目标。2,000 张照片的真实浏览器-后端工作流仍是未来/手动目标，有意不纳入默认 E2E 路径。

已验证的真实工作流步骤：

- 使用本地项目数据文件夹创建项目。
- 通过真实后端导入默认 100 张或可选启用的 500 张生成合成 JPEG 文件。
- 真实后端处理与分组完成，失败项为零。
- 真实预览资源被服务到浏览器筛选工作区。
- 通过真实 API 更新 Pick 状态。
- 在真实工作区切换 Picks 筛选器。
- 在真实工作区进行分组导航。
- CSV 导出就绪，并带有浏览器下载链接。

仍未验证的内容：

- 2,000 张照片的真实浏览器-后端运行。
- 全分辨率相机 JPEG 的解码、传输和浏览器内存行为。
- 完整浏览器进程 RSS、GPU 内存、图像解码内存，以及操作系统内存压力。
- 长时间审阅会话中的重复筛选器更改、状态更新、对比模式和全部加载行为。

插桩说明：Chromium 运行现在会在可用时通过 Playwright CDP 收集 `Performance.getMetrics`。该 smoke 会记录 `JSHeapUsedSize`、`JSHeapTotalSize`、`Nodes`、`Documents`、`Frames`、`LayoutCount`、`RecalcStyleCount`、`TaskDuration`、`ScriptDuration`、`LayoutDuration` 和 `RecalcStyleDuration`；不可用的指标记录为 `null`，而不是让测试失败。该 smoke 还会在可用时记录文档 DOM 节点数，以及浏览器暴露的 `performance.memory` JS 堆估计值。

浏览器内存说明：报告的堆值来自 Chromium `performance.memory`，只是 JS 堆估计值。它不是完整浏览器进程内存、已解码图像内存、GPU 内存，也不是跨浏览器指标。DOM 节点数只是文档元素计数；它不测量已解码图像内存、GPU 资源、屏幕外浏览器内部状态，或操作系统内存压力。

- 该基准使用生成的合成 JPEG，而不是精选的真实相机照片集。

发布就绪决定：在本机上，对生成的小图和生成的 3000x2000 JPEG 而言，1,000 张照片真实浏览器-后端验证现在可接受。2,000 张照片真实浏览器-后端运行不应成为下一个默认门槛。只有在有更长的本地验证窗口，或导入架构工作降低了主导导入阶段成本之后，才应将其作为显式手动基准尝试。当前导入架构在跨 API 进程退出的持久性方面仍需更多工作，才能被视为可靠。
