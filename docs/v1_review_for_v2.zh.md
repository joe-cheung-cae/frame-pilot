# FramePilot v1 评审，用于 v2 规划

> 语言：[English](v1_review_for_v2.md) | **中文**

## 1. 执行摘要

- FramePilot v1 是一个可用的 MVP，还不是生产就绪软件。它展示了完整的本地优先筛选循环，但尚未针对真实摄影师规模的批次、长时间处理或专业工作流期望做过验证。
- v1 已经把最重要的 MVP 事情做好了：项目创建、本地图像导入、导入时复制（copy-on-import）安全、生成缩略图/预览、确定性评分、简单分组、推荐解释、手工复核状态、星级评分，以及 CSV/文件夹/ZIP 导出。
- 后端紧凑且易懂。主要实现位于 `apps/api/app/api/routes.py`、`apps/api/app/services/importing.py`、`apps/api/app/services/processing.py`、`apps/api/app/services/grouping.py`、`apps/api/app/services/ranking.py` 和 `apps/api/app/services/exporting.py`。
- 前端覆盖了从首页到导入、处理、筛选和导出的预定页面流。主要工作区是 `apps/web/src/components/CullingWorkspace.tsx`。
- v1 已不足以支撑 v2，因为处理是同步的、图像分析只有启发式、相似分组过浅、大批量性能未经证明，而且 UI 仍是浏览器 MVP，而不是面向高容量筛选的严肃工作区。
- 应保留本地优先姿态、原片安全、确定性基线算法、透明评分、简单 API 形态，以及对评分、分组、状态更新和导出的聚焦测试覆盖。
- 应重新设计处理编排、进度报告、导入模型、分组质量、复核状态架构、导出/互操作行为，以及面向真实本地工作流的测试策略。
- v2 应在结构化分支上演进 v1，而不是丢弃仓库。现有代码是很好的脚手架，但在加入重大产品功能之前，若干核心区域应先重构。

## 2. 仓库结构评审

根级结构：

- `README.md` 说明当前 MVP、本地设置、隐私立场、工作流和验证命令。
- `develop_plan.md` 定义产品范围、MVP 工作流、本地优先约束、评分公式、UI 要求和范围外事项。
- `AGENTS.md` 包含仓库特定的实现约束。
- `package.json` 拥有后端、前端、测试、lint、typecheck 和 E2E 的 monorepo 风格脚本。
- `docs/` 当前包含 `architecture.md`、`api.md` 和 `scoring.md`。
- `apps/api/` 包含 FastAPI 后端。
- `apps/web/` 包含 Next.js 前端。
- `tests/e2e/` 包含 Playwright 测试。
- `scripts/run-e2e.sh` 包装 Playwright 执行。

前端结构：

- `apps/web/src/app/` 定义首页、项目创建、导入、处理、筛选和导出的 Next.js 页面。
- `apps/web/src/components/` 包含主要 UI 组件：`ProjectCreator`、`ProjectList`、`ImportPanel`、`ProcessingPanel`、`CullingWorkspace`、`ExportPanel`、`Shell` 和 `Providers`。
- `apps/web/src/lib/` 包含 API 客户端类型/辅助函数，以及用于项目路由、复核导航和导出状态计数的小型已测工具。
- `apps/web/src/store/reviewStore.ts` 包含用于筛选 UI 状态的小型 Zustand store。

后端结构：

- `apps/api/app/main.py` 创建 FastAPI 应用、CORS 策略、健康路由和 API 路由器。
- `apps/api/app/api/routes.py` 包含所有 HTTP 路由处理程序。
- `apps/api/app/models/entities.py` 定义 `Project`、`Photo`、`PhotoGroup`、`ProcessingJob` 和 `ExportRecord` 的 SQLModel 表。
- `apps/api/app/schemas/api.py` 定义 Pydantic 请求/响应模式和校验器。
- `apps/api/app/services/` 包含项目创建、导入、处理、分组、排序和导出服务。
- `apps/api/app/image/scoring.py` 包含确定性技术评分和人脸/眼睛启发式。
- `apps/api/app/ai/embeddings.py` 包含当前的感知哈希/颜色嵌入近似。
- `apps/api/app/db/session.py` 拥有 SQLite 引擎/会话创建，以及导出记录的一次兼容性迁移。

测试结构：

- `apps/api/tests/` 包含后端单元和 API 测试，覆盖项目、评分、分组、排序、导入/处理/导出工作流、导出安全和状态更新。
- `apps/web/src/lib/*.test.ts` 包含前端纯辅助函数的轻量 Node 测试。
- `tests/e2e/local-workflow.spec.ts` 使用模拟的 API 路由做浏览器工作流。
- `tests/e2e/real-local-smoke.spec.ts` 使用真实本地 API 和 web 应用，做小型导入/处理/精选/导出 smoke 流程。

文档结构：

- `docs/architecture.md` 准确描述当前双应用架构和本地项目存储布局。
- `docs/api.md` 记录已实现的 API 端点和响应形态。
- `docs/scoring.md` 记录确定性评分和实验性人脸/眼睛启发式。

脚本和开发者工作流：

- `npm run dev` 通过 `concurrently` 同时启动后端和前端。
- `npm run test` 运行后端 pytest 加上前端单元测试和生产构建。
- `npm run test:e2e` 通过 `scripts/run-e2e.sh` 运行 Playwright。
- `npm run verify` 运行 lint、typecheck 和测试。

该结构适合作为 v2 基础工作，但 v2 应按更清晰的边界重组：后台任务、存储服务、导入源、分析流水线、API 版本控制，以及更大的前端工作区组件。当前布局仍足够易懂，可以增量演进。

## 4. 后端评审

FastAPI 路由设计：

- 现有情况：`apps/api/app/api/routes.py` 在 `/api` 下暴露项目、导入、处理、任务、照片、组、导出、下载和生成资源路由。路由集合与 `docs/api.md` 一致。
- 弱点：所有路由都在一个文件中，导出创建同步写入产物，处理在一次请求内启动并完成，且没有 API 版本前缀。
- 用户风险：大导入、处理或导出可能阻塞请求，使 UI 看起来卡住或失败。
- v2 动作：按资源拆分路由模块，为变更行为引入 `/api/v2` 或版本化契约，并把处理/导出工作移到后台任务。

SQLModel 数据模型：

- 现有情况：`Project`、`Photo`、`PhotoGroup`、`ProcessingJob` 和 `ExportRecord` 定义在 `apps/api/app/models/entities.py`。
- 弱点：状态字段是普通字符串，嵌入和导出状态是 JSON 字符串，迁移仅限于 `apps/api/app/db/session.py` 中的 `_ensure_export_record_columns`。
- 用户风险：字符串漂移、数据库边界处校验弱，以及 v2 演进时脆弱的 schema 变更。
- v2 动作：引入枚举、在有用处使用结构化 JSON 辅助或规范化记录，以及适合 SQLite 的简单迁移计划。

项目存储布局：

- 现有情况：每个项目有 `originals/`、`thumbnails/`、`previews/`、`exports/` 和 `cache/`，由 `create_project` 创建。
- 弱点：v1 通过浏览器导入时总是把上传复制进项目。没有原地引用（reference-in-place）模式、sidecar 元数据目录、可恢复的衍生缓存或源文件夹跟踪。
- 用户风险：大型拍摄会消耗重复磁盘空间，用户不容易理解 FramePilot 是在复制还是引用原片。
- v2 动作：决定复制 vs 引用的产品策略，然后在项目元数据和 UI 中显式编码。

导入流水线：

- 现有情况：`import_image_file` 校验扩展名，写入上传文件，用 Pillow 打开，提取元数据，创建衍生文件，给图像评分，计算嵌入，使过期处理失效，并提交一条 `Photo`。
- 弱点：导入是同步且按文件进行的。它在一次请求中把上传读入内存/文件，在导入期间计算全部分析，并在每个文件之后使所有组/推荐元数据失效。
- 用户风险：大批次可能超时或感觉冻结；部分进度和重试有限。
- v2 动作：把导入登记、衍生生成、评分、嵌入、分组和排序拆成可恢复的任务步骤。

图像衍生生成：

- 现有情况：缩略图和预览作为 WebP 在 `_save_derivatives` 中生成。
- 弱点：衍生生成是立即的、不可恢复的，且没有独立跟踪。除了唯一输出路径外，没有缓存失效模型。
- 用户风险：失败或中断的批次可能需要返工；进度无法显示衍生级细节。
- v2 动作：让衍生记录或处理状态显式化，并在有界批次中处理衍生文件。

元数据提取：

- 现有情况：`_extract_metadata` 读取常见 EXIF 值，例如拍摄时间、相机型号、镜头、焦距、光圈、快门速度和 ISO。
- 弱点：它不处理更丰富的 EXIF 变体、时区、sidecar 数据、RAW 元数据或相机特定怪癖。
- 用户风险：按拍摄时间/相机分组对真实拍摄可能错误或缺失。
- v2 动作：改进元数据解析，并记录元数据的置信度/来源。

评分流水线：

- 现有情况：`compute_quality_scores` 从 NumPy 数组计算确定性值。
- 弱点：评分校准是全局的，并由合成测试驱动。噪声评分过于简单，审美分数是曝光/对比度平均值，人脸评分是实验性的。
- 用户风险：对肖像、低光工作、高 ISO 图像、有意模糊的镜头或创意曝光，推荐可能具有误导性。
- v2 动作：把确定性技术指标保留为可解释基线，用合成和真实样本集增加校准测试，并稍后考虑可选的本地模型。

分组流水线：

- 现有情况：`group_similar_photos` 按拍摄时间或文件名排序，并且只用余弦相似度阈值与前一项比较。
- 弱点：除排序外不使用文件名序列邻近性，不使用相机/镜头/尺寸，当相关帧不相邻时可能错误拆分或合并。
- 用户风险：连拍被拆开、无关场景被分到一组，或代表选择很差时，用户会失去信任。
- v2 动作：围绕候选窗口、元数据特征、感知哈希和校准阈值重新设计分组。

推荐流水线：

- 现有情况：`rank_group` 应用透明权重，并用基于规则的解释分配 Pick/Maybe/Reject。
- 弱点：对所有非单张组的重复惩罚是平坦的，当启发式错误时人脸质量可能主导，用户偏好不影响排序。
- 用户风险：错误的自动推荐会拖慢复核，而不是加速。
- v2 动作：保留解释，但改进排序输入、组感知惩罚，并允许可配置的排序配置文件。

导出流水线：

- 现有情况：CSV、文件夹复制和 ZIP 导出在 `exporting.py` 中实现；下载路由检查 CSV/ZIP 产物解析后位于项目导出根目录内。
- 弱点：文件夹导出只显示本地输出路径，CSV 格式尚未面向 sidecar/XMP，导出同步运行。
- 用户风险：大导出可能阻塞；专业互操作有限。
- v2 动作：加入排队导出、sidecar 元数据格式、更清晰的下载/打开文件夹 UX，以及导出历史管理。

任务/进度模型：

- 现有情况：`ProcessingJob` 记录由 `process_project` 创建、更新并返回。
- 弱点：尽管有模型，任务仍是同步的。前端在请求完成后才收到最终任务，因此进度并不是真正实时的。
- 用户风险：处理数千张图像可能看起来已损坏。
- v2 动作：实现带轮询或 server-sent events 的后台队列；存储步骤级进度和可恢复状态。

错误处理：

- 现有情况：导入捕获不支持/不可读图像并清理已写入文件。处理捕获异常并将任务标记为失败。API 校验在适当时返回 422/404。
- 弱点：处理把详细的结构化错误吞进 `error_message`；多文件导入返回跳过原因但没有重试 ID；记录创建后的导出失败没有用失败导出状态处理。
- 用户风险：用户可能不知道哪一个文件导致失败，或如何重试。
- v2 动作：为导入、处理和导出添加结构化错误和失败项记录。

数据校验：

- 现有情况：Pydantic 校验项目名称、状态更新、星级评分、导出模式和导出状态。
- 弱点：如果内部写入，DB 模型字符串字段仍允许无效值，项目 `root_path` 也没有被严格约束。
- 用户风险：内部缺陷或未来迁移后可能出现不一致数据。
- v2 动作：加入枚举、路径策略校验和更强的存储安全检查。

文件安全：

- 现有情况：文件名用 `Path(filename).name` 规范化，重复名称获得后缀，原片被复制而不是修改，导入清理已测试，导出下载被约束到导出根目录。
- 弱点：生成资源服务从 `project.root_path`、`kind` 和 basename 构建路径，但只检查存在性，不检查 `resolve().is_relative_to(...)`。删除项目会移除 DB 记录，但不移除文件。
- 用户风险：如果项目元数据损坏，存在低到中等的文件暴露风险；删除后磁盘堆积。
- v2 动作：对所有文件服务路径应用一致的解析根（resolved-root）检查，定义项目删除/归档语义，并测试路径穿越情况。

测试覆盖：

- 现有情况：后端测试覆盖了可观的 MVP 表面，包括文件安全、重复文件名、导出、处理失效、排序解释和状态更新。
- 弱点：没有性能测试、没有大批量测试、真实 E2E 有限、前端组件测试有限，也没有真实照片数据集。
- 用户风险：v2 回归可能隐藏在 UX 和规模行为中。
- v2 动作：保留当前测试，并增加夹具数据集、真实 E2E 流程、性能 smoke 检查和工作区组件级测试。

## 5. 前端评审

页面流：

- 现有情况：Next.js 页面覆盖首页、`/projects/new`、导入、处理、筛选和导出。
- 弱点：流程是线性和简单的；回到部分完成的工作或管理许多项目都只是基础能力。
- 用户风险：有多次拍摄的真实用户可能觉得导航很浅。
- v2 动作：加入项目仪表盘、更清晰的项目状态，以及可恢复的工作流链接。

项目创建 UX：

- 现有情况：`ProjectCreator` 收集项目名称并重定向到导入。
- 弱点：尽管后端接受 `root_path`，UI 中没有根路径选择；没有显式的复制/引用策略。
- 用户风险：用户可能不知道项目数据存储在哪里。
- v2 动作：一旦产品策略确定，就暴露存储选择。

导入 UX：

- 现有情况：`ImportPanel` 支持文件选择和通过 `webkitdirectory` 的浏览器文件夹选择，显示跳过的文件，并预览最近导入。
- 弱点：浏览器文件夹导入不同于桌面式文件夹引用；没有批次队列、按文件进度、重试或文件夹重新扫描。
- 用户风险：大文件夹导入可能缓慢、不透明且难以恢复。
- v2 动作：转向带进度的排队导入；如果产品仍基于浏览器，就清楚记录浏览器限制。

处理 UX：

- 现有情况：`ProcessingPanel` 触发处理，并从已完成的响应显示任务状态。
- 弱点：因为后端是同步的，进度条在实际处理期间不是实时的。
- 用户风险：大批次时 UI 会感觉冻结。
- v2 动作：轮询后台任务，并显示当前文件/步骤、若可用则显示 ETA、暂停/取消/重试，以及失败细节。

筛选工作区 UX：

- 现有情况：`CullingWorkspace` 有左侧过滤器/组面板、中间预览、右侧评分/解释面板、顶部工具栏和底部胶片条。
- 弱点：该组件有 414 行，并拥有数据获取、过滤、键盘处理、变更、选择和布局。它没有虚拟化，对比/缩放行为有限。

- v2 动作：拆成工作区外壳、组列表、胶片条、预览、详情面板、键盘控制器和复核状态模块；加入虚拟化。

## 6. 算法评审

锐度分数：

- 当前方法：在 `compute_quality_scores` 中对亮度做简单 Laplacian 方差。
- 保留：对明显模糊有用的确定性基线。
- v2 关注：未针对传感器尺寸、缩放、锐化、噪声或主体区域锐度校准。

模糊分数：

- 当前方法：归一化锐度的倒数。
- 保留：简单可解释的风险指示器。
- v2 关注：全局模糊可能惩罚有意运动或浅景深。

曝光分数：

- 当前方法：平均亮度到中灰的距离。
- 保留：对明显曝光失败有用。
- v2 关注：平均亮度对高调、低调、逆光、夜景和舞台摄影偏弱。

对比度分数：

- 当前方法：归一化亮度标准差。
- 保留：简单技术信号。
- v2 关注：可能奖励刺眼对比，或惩罚有意扁平的场景。

噪声分数：

- 当前方法：高频亮度偏差估计。
- 仅作为弱启发式保留。
- v2 关注：它把细节、纹理、锐化和噪声混在一起。

人脸/睁眼启发式：

- 当前方法：肤色掩膜、候选边界框检查、人脸区域锐度，以及眼区中的暗部细节。
- 仅作为明确实验性的 MVP 信号保留。
- v2 关注：对生产级肖像筛选过弱，并很可能受光照、肤色、调色、姿势、尺度和遮挡偏置。
- v2 动作：稍后用可选的本地人脸/关键点/眼睛模型替换，或在可靠之前从排序中移除。

审美分数：

- 当前方法：曝光和对比度的平均值。
- 仅作为占位符保留。
- v2 关注：它不是真正的审美模型。
- v2 动作：若保留则重命名或重新校准；稍后可以引入可选的轻量本地审美模型，且不捆绑大模型文件。

嵌入或相似近似：

- 当前方法：`image_embedding` 把 64 位感知哈希与 8x8 RGB 采样组合，并归一化向量。
- 保留：对小型确定性近重复实验有用。
- v2 关注：对稳健的连拍分组、裁剪/姿势变化、曝光变化和非相邻重复过弱。
- v2 动作：在可选的本地模型嵌入之前，组合感知哈希、颜色/布局描述符、元数据和候选窗口。

分组阈值策略：

- 当前方法：用余弦相似度阈值 `0.96` 和最大时间间隔 30 秒比较相邻排序后的照片。
- 保留：确定性基线测试。
- v2 关注：仅相邻比较很脆弱，阈值也未对照真实数据集校准。
- v2 动作：构建带可配置阈值、元数据特征和质量指标的已测分组策略。

排序公式：

- 当前方法：`final_score = 0.30 * sharpness + 0.20 * exposure + 0.20 * face_quality + 0.20 * aesthetic - 0.10 * duplicate_penalty`。
- 保留：透明、可由代码配置的加权。
- v2 关注：输入偏弱，重复惩罚过于简单。
- v2 动作：保留透明排序，但改进指标并允许题材/配置文件配置。

推荐解释：

- 当前方法：`ranking.py` 中基于规则的最强/最弱指标文本。
- 保留：良好的产品原则和本地优先。
- v2 关注：解释质量取决于弱指标。
- v2 动作：继续基于规则的解释；不要为 MVP/v2 要求 LLM。

可选 AI 模型：

- 稍后的好候选：轻量本地人脸/关键点/眼睛状态、审美质量、语义模糊/主体检测，或更好的嵌入。
- 约束：不要把大捆绑模型文件加入仓库。如果允许模型，应做成可选的本地下载或用户提供的资源。

仍更偏好无模型算法：

- 衍生生成、EXIF 解析、文件安全、基本锐度/曝光/对比度、感知哈希、文件名序列分析和导出逻辑应保持确定性和可测试。

## 7. 性能与可扩展性评审

100 张照片：

- v1 在普通机器上对 JPEG/PNG/WebP 大概应能处理这个规模。
- 风险区域主要是 UX 打磨和同步请求时长。

500 张照片：

- v1 可能能工作，但会变得不舒服。导入在上传处理期间做评分、衍生和嵌入。处理是同步的，并在创建组时反复提交。
- 前端胶片条和照片数组没有虚拟化。

2,000 张照片：

- 尽管 `develop_plan.md` 中有该产品场景，v1 并未针对这个目标做过真实验证。
- 同步导入/处理/导出是主要限制。浏览器工作区可能渲染过多缩略图和组按钮。

10,000 张照片：

- v1 不适合。磁盘使用、衍生生成时间、SQLite 访问模式、内存、前端渲染、导出时长和恢复行为都需要 v2 设计工作。

同步处理限制：

- `process_project` 完全在请求内运行。任务模型存在，但不提供实时进度。
- v2 应在考虑更复杂系统之前，使用后台工作器或带持久任务记录的进程内队列。

内存使用风险：

- 导入把每张图像转换为 RGB 和 NumPy 数组。一次一张没问题，但大图和并发上传会给内存施压。
- 前端通过 API 查询加载所有照片/组，并渲染所有可见缩略图。

缩略图生成成本：

- 缩略图和预览生成在导入期间立即发生。
- v2 应以有界并发和可恢复的项状态处理衍生文件。

数据库查询风险：

- v1 使用简单 SQLModel 查询，小规模应没问题。
- 对成千上万张照片，v2 需要项目/组/状态/推荐排序的索引，以及谨慎的分页或过滤查询。

前端渲染风险：

- `CullingWorkspace` 直接映射所有组和所有可见照片。
- v2 应虚拟化胶片条和组列表，并尽可能避免每次状态更新后重新获取完整照片集。

导出风险：

- CSV、ZIP 和文件夹导出是同步的。为成千上万张原片创建 ZIP 可能耗时很长。
- v2 应对导出排队并显示导出进度/历史。

长时间任务 UX：

- v1 状态 UI 无法在请求仍挂起时显示真实进度。
- v2 应暴露持久进度并允许重试/恢复。

实用的 v2 架构改进：

- 加入简单的本地任务队列、项级处理状态、有界并发、轮询端点、分页/过滤和虚拟化 UI 列表。
- 避免用分布式队列或云服务过度工程化。早期 v2 用单进程本地工作器就足够。

## 10. v1 限制

- 严重：`process_project` 中的同步处理阻塞长时间工作，并阻止真正的实时进度。
- 严重：对 2,000 到 10,000 张照片这类大批次验证不足。
- 高：`group_similar_photos` 中的相似分组对真实连拍和近重复工作流过弱。
- 高：`_detect_face_signals` 中的人脸/睁眼启发式过弱，不足以驱动严肃的肖像排序。
- 高：`CullingWorkspace.tsx` 中的筛选工作区可维护性和渲染性能风险。
- 高：真实 E2E 验证不足；当前真实本地 smoke 测试有用但狭窄。
- 高：导入、处理和导出的进度与恢复行为有限。
- 中：文件格式支持有限；仅 JPEG/PNG/WebP，没有 RAW 或 HEIC 工作流。
- 中：元数据提取基础，可能错过真实相机数据。
- 中：导出/下载 UX 有限，尤其是文件夹导出和专业 sidecar 格式。
- 中：当前任务模型存在，但并非真正异步或可恢复。
- 中：生成资源服务应使用更严格的解析根（resolved-root）路径检查。
- 中：前端测试覆盖在纯辅助函数之外很薄。
- 中：没有性能测试或校准过的合成/真实图像数据集。
- 低：文档对 v1 良好，但缺少 v2 产品、架构、算法、测试和迁移文档。
- 低：所有后端路由都在单个路由文件中，现在还可管理，但 v2 应拆分。

## 11. 推荐的 v2 产品方向

v2 应成为严肃的本地照片筛选工具，而不只是演示。主要方向应是本地优先、高容量、可恢复，并面向摄影师。

现在推荐：

- 在做出桌面包装决策之前，保持当前本地 Web 架构的同时，提供更像桌面的本地优先工作流。
- 带显式项目存储策略的更好批次导入。
- 带持久进度和重试的后台处理。
- 更强的重复/连拍分组。
- 更好的筛选工作区人机工学，包括缩放、对比、组优先复核和虚拟化。
- 带排队导出和更清晰输出处理的更好导出工作流。
- 扩展的真实本地 E2E 和性能验证。

基础之后推荐：

- Sidecar 元数据导出，若产品负责人确认 Lightroom/Capture One 互操作，则很可能是 XMP。
- 若需要，可选的 HEIC 和 RAW 预览支持。
- 用于人脸/眼睛、嵌入或审美的可选轻量本地 AI 模型。
- 仅在排序和工作流基础可靠之后，才做用户偏好学习。

推迟：

- 云同步、账户、支付、协作、移动端和大捆绑模型。
- 在 v2 拥有稳定数据集和用户工作流之前，推迟高级个性化模型训练。

## 12. v2 架构提案

从 v1 保留：

- 本地优先项目存储。
- 导入时复制安全，除非产品负责人选择原地引用。
- SQLite 作为本地元数据数据库。
- 后端使用 FastAPI 和 SQLModel。
- 前端使用 Next.js/React，除非产品负责人选择桌面包装。
- 确定性基线指标和基于规则的解释。
- 当前导出模式作为基线功能。

重构：

- 把 `routes.py` 拆成资源模块。
- 把 `CullingWorkspace.tsx` 拆成更小的组件和控制器。
- 把导入、衍生、评分、嵌入、分组、排序和导出步骤提取为任务操作。
- 在适当时用类型化辅助或规范化记录替换嵌入/状态的 JSON 字符串。

重新设计：

- 处理架构、进度模型、分组策略、工作区状态、导出 UX 和大型列表渲染。

后端处理架构：

- 先使用简单的本地任务队列。带持久 SQLite 任务/项状态的单进程工作器对 v2.0/v2.1 已足够。
- 把任务建模为导入、衍生、评分、分组、排序和导出任务。
- 存储项级状态，以便中断的运行可以恢复。
- 对图像工作使用有界并发。

前端状态架构：

- 保留 React Query 用于服务端数据。
- 保留小型本地 store 用于视图状态，但拆分选择、过滤器、键盘和预览状态。
- 对状态/星级变更谨慎使用乐观更新。
- 加入虚拟化的组和胶片条列表。

存储布局：

- 保留项目子目录，但在需要时加入显式的 `sidecars/`、结构化 `cache/` 和任务产物。
- 决定 `originals/` 是仅表示已复制原片，还是允许原地引用项目。

任务队列/后台处理方式：

- 从进程内本地工作器和轮询端点开始。
- 早期 v2 避免 Celery/云队列。
- 在高级调度之前加入取消/重试/恢复。

数据库迁移方式：

- 加入有文档的 SQLite 迁移系统。小型 Alembic 设置或显式迁移运行器都可以接受。
- 在数据库中记录 schema 版本。

API 版本控制方式：

- 若可能，在过渡期间保留 v1 端点。
- 如果请求/响应形态发生实质变化，为面向任务的契约加入 `/api/v2`。

测试方式：

- 先扩展后端测试，覆盖任务和存储安全。
- 加入使用本地生成图像的真实 E2E 流程。
- 在默认快速测试套件之外加入性能 smoke 测试。

文档方式：

- 在重大代码变更之前，创建产品需求、架构、里程碑、算法策略、测试策略和迁移计划。

## 13. v2 里程碑提案

### v2.0 基础

- 目标：让代码库为 v2 变更做好准备，且不改变核心行为。
- 任务：拆分路由模块，拆分筛选工作区组件，加入 schema 版本控制计划，记录存储策略，加入缺失的文件安全测试。
- 验收标准：现有 v1 行为仍通过；最终 diff 可理解且低风险。
- 测试要求：`npm run test`、相关 E2E smoke、lint、typecheck。
- 风险：没有产品改进的重构搅动。

### v2.1 处理与进度

- 目标：用持久后台任务替换同步处理。
- 任务：加入任务/项表、工作器循环、轮询端点、处理恢复、结构化错误，以及前端进度轮询。
- 验收标准：处理显示实时进度，并能从中断中恢复。
- 测试要求：后端任务测试、API 处理测试、真实 E2E 处理流程。
- 风险：并发缺陷和 SQLite 锁。

### v2.2 筛选工作区升级

- 目标：改进高容量复核 UX。
- 任务：虚拟化胶片条/组列表，拆分工作区组件，缩放/适应控件，对比模式，更强的键盘控制器，更好的加载/错误状态。
- 验收标准：工作区在至少 2,000 张合成照片时仍保持响应。
- 测试要求：组件测试、E2E 键盘/状态测试、无障碍检查。
- 风险：UI 复杂性和状态同步缺陷。

### v2.3 导出与互操作

- 目标：让导出专业且有弹性。
- 任务：排队导出、导出历史、文件夹/打开路径 UX、CSV 改进，以及若需要则可选 sidecar/XMP。
- 验收标准：大导出显示进度，可以重试，并产生已校验产物。
- 测试要求：导出队列测试、CSV/ZIP/文件夹测试、E2E 下载校验。
- 风险：平台特定的文件夹行为和互操作范围蔓延。

### v2.4 算法质量升级

- 目标：提高分组和排序信任。
- 任务：更好的感知描述符、元数据感知分组、阈值校准、排序配置文件、置信度感知的解释。
- 验收标准：分组/排序在定义的合成和真实样本集上改进。
- 测试要求：数据集驱动测试和算法回归报告。
- 风险：对小数据集过拟合。

### v2.5 性能与可靠性

- 目标：为成千上万张照片做验证和调优。
- 任务：分页/过滤、查询索引、有界图像并发、导出性能、内存监控、重启/恢复测试。
- 验收标准：为 500、2,000 和目标最大批次大小记录性能。
- 测试要求：性能 smoke 脚本和可靠性 E2E。
- 风险：依赖机器的测量。

### v2.6 可选 RAW/HEIC 和 AI 模型支持

- 目标：仅在产品负责人确认需要时加入高级格式/模型支持。
- 任务：RAW/HEIC 预览提取、可选模型下载/配置、无模型回退、文档。
- 验收标准：不提交大模型；不受支持的系统仍能运行基线工作流。
- 测试要求：格式夹具、可选依赖测试、回退测试。
- 风险：依赖重量、平台差异和支持负担。

## 17. 最终建议

FramePilot 应在结构化 v2 分支上增量演进 v1，而不是从头开始。当前仓库已有足够正确的本地优先行为、测试和文档，可以作为坚实基础。然而，v2 不应只是在当前同步 MVP 上叠加功能。

推荐的第一个分支名：

- `codex/v2-foundation-review`

现在还不应做的事：

- 在产品负责人确认之前，不要实现 RAW/HEIC 支持。
- 不要加入大捆绑 AI 模型。
- 不要加入云同步、登录、支付或远程服务要求。
- 不要整体重写前端或后端。
- 除非产品负责人已批准 v2 方向，否则不要一次创建全部 v2 文档。

本次评审之后应立即做的事：

- 确认产品负责人关于平台、目标批次大小、复制 vs 引用存储、RAW/HEIC、XMP 导出和可选 AI 模型策略的回答。
- 创建 v2 产品需求和架构文档。
- 以行为保持的重构和安全测试开始 v2.0 基础工作。
- 然后在更深的算法或 UI 升级之前，实现后台处理和真实进度。

简洁评审摘要：

- v1 是可用的本地优先 MVP，后端测试扎实，工作流完整。
- v1 对严肃照片筛选还不是生产就绪，因为处理、分组、排序质量、UI 规模和真实 E2E/性能验证需要 v2 工作。
- 保留本地优先架构、原片安全、确定性基线指标、透明推荐和当前导出基线。
- 为真实批次重新设计处理/进度、分组、工作区架构、导出互操作和测试覆盖。
